## 四、四份替代品各自能补什么

**GDD-CN 八段式** —— 补的是「单系统策划案该怎么写、写到什么程度算写完」。
八段:系统概述 / 设计目的与体验目标 / 详细规则 / 公式与数值 / 配置表结构与可调项 / 边界情况 / 依赖与接口 / 验收标准。
其中两条跟本项目直接对得上:
- 「文档写规则,数值进表」——凡策划能改的数字必须落到配置表字段,正文不留裸数值。本项目已有同一条铁律(数值全走 Godot `Resource` `.tres`)。
- 「没你确认,不落盘」「不推翻已有结论」——正好是本项目「Mavis 只出结构、不代写正文、不代做决策」的通用版表述。

**GDD 九段式** —— 补的是「整份 GDD 的骨架长什么样」。
九段:设计首页 / 玩法走读 / 核心机制 / 内容系统 / 界面规划 / 音效与音乐 / 视觉风格 / 数值配置 / 变更记录。
两个点值得注意:
- 第八段要求**所有数值标注来源**(设计初值 / 已验证 / 待校准)——比「有数值」更进一步,能看出哪些数还没校准。
- 第二段「玩法走读」要求写一段 **60-120 秒连续片段**,覆盖目标→第一眼信息→一次核心输入→一次需要比较的选择→选择的代价→局面改变→一次小成功/失败。这是「讲清一个战斗回合长什么样」的现成写法。

**AI Game Design 工作流** —— 补的是「从文档走到能玩的东西」中间那一段。
链路:原始想法→玩家幻想→核心循环→机制→规则与约束→功能范围→精简 GDD→原型计划→生产里程碑→游戏测试反馈→迭代计划。
关键主张:
- 核心循环必须能说清 **30 秒 / 5 分钟 / 30 分钟** 三档时间尺度各在干什么。
- 范围要做减法:功能清单分 Must-have / Should-have / Could-have / Cut,第一版可玩只需要够回答一个问题——「核心体验值得建造吗?」
- 里程碑表:GDD 解释游戏是什么,**生产计划解释怎么造它**;设计只有具备任务、依赖关系和完成标准后才能投产。

**数值策划白皮书** —— 补的是「数值取值时该守哪些区间」。
可直用的几条:数字敏感区间 0.1~10000000;概率正常认知区间 1%~80%,>80% 视为必发生(建议直接伪概率必成功);养成类概率变化区间 5%~60%,最敏感段 10%~50%;成长幅度过小要用阶段性效果弥补;日常产出数量级至少 10+;战斗技能 CD 建议 5~60 秒。
> 注意:这份是**手游商业化**语境,概率/付费档位那几节对本项目参考价值有限,「数字区间 / 概率认知 / 成长幅度 / 产出量级」这几条通用。
